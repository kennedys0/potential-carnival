# 2. ABSOLUTE ENGINEERING PRINCIPLES

This software may eventually control real financial assets.

Therefore, correctness takes priority over trading performance.

## Non-negotiable rules

- Never confuse blockchain confirmation with completed accounting.
- Never fabricate executed quantities.
- Never infer an on-chain failure solely from a timeout.
- Never treat missing blockchain evidence as proof that a transaction failed.
- Never permit conflicting transactions against unresolved inventory.
- Never bypass database constraints using Redis state.
- Never update financial inventory from unexplained balance discrepancies.
- Never convert unsafe raw blockchain integers through JavaScript floating-point values.
- Never allow duplicate callbacks to authorize duplicate withdrawals.
- Never trust AI-generated financial parameters without deterministic validation.
- Never use a mock test as evidence of PostgreSQL concurrency correctness.
- Never hide failed tests or silently increase regression baselines.
- Never claim formal verification without actually performing formal verification.
- Never enable live trading as part of this task.

**Critical distinction:**

A system that compiles is not necessarily correct.

A system with passing unit tests is not necessarily financially safe.

A system using PostgreSQL transactions is not automatically idempotent.

A system using unique constraints is not automatically free from double execution.

A system returning `SUCCESS` is not automatically reconciled.

All safety claims must be supported by implementation evidence and appropriate tests.

# 4. P0 — DATABASE MUST BECOME THE FINANCIAL SOURCE OF TRUTH

## Finding R9-001: Atomic SQL does not fully validate financial quantities

The R8 audit identified that `atomic_reconcile_exit` can receive absolute inventory and PnL values calculated from application-side state.

This can create incorrect accounting if the application uses stale position data.

## Required implementation

Build a database-authoritative accounting finalization process.

It must:

1. Identify the confirmed execution attempt.
2. Identify the verified transaction signature.
3. Identify the related trade.
4. Lock the relevant database rows.
5. Verify the attempt belongs to that trade.
6. Verify the transaction has not already been applied.
7. Verify the permitted lifecycle transition.
8. Read current remaining inventory under the lock.
9. Read the verified fill quantity and proceeds.
10. Validate that the inventory movement is allowed.
11. Calculate updated inventory and cost basis.
12. Update realized PnL.
13. Insert immutable fill evidence.
14. Update the position.
15. Finalize the execution attempt.
16. Commit all related changes atomically.

The SQL must not blindly trust stale absolute remaining quantities supplied by the application.

### Critical financial invariants

```text
remaining_raw >= 0

filled_sell_raw <= available_reserved_inventory

confirmed_fill_applied_count <= 1

initial_inventory
+ verified_acquisitions
- verified_disposals
+ separately_recorded_adjustments
= reconciled_inventory
```

Track protocol-specific transfer fees and other legitimate inventory movements separately.

### Idempotency

Calling the financial finalization function twice with the same confirmed fill must not deduct inventory twice.

The function should return an explicit result:

```text
APPLIED
ALREADY_APPLIED
CONFLICT
INVALID_STATE
INVALID_EVIDENCE
INSUFFICIENT_INVENTORY
```

Define the exact return contract in the implementation.

### PostgreSQL requirements

Use appropriate:

- Row-level locking
- Unique constraints
- Foreign keys
- Check constraints
- Transaction isolation
- Version validation
- Immutable ledger records

Never hold a database transaction open while awaiting a remote Solana RPC request.

Verify database behavior using real PostgreSQL, not mocked repository functions.

# 5. P0 — REBUILD INVENTORY RECONCILIATION

## Finding R9-002: Wallet balance discrepancies incorrectly modify positions

R8 still contains logic that can reduce database inventory when wallet token balances are lower than expected.

The previous implementation includes FIFO allocation of missing tokens across positions.

This behavior must be eliminated unless an explicitly verified transaction supports the financial adjustment.

## Required architecture

Separate three concepts:

### A. On-chain wallet inventory

What the wallet currently owns according to verified blockchain account state.

### B. Internal position inventory

What the trading ledger attributes to active trading positions.

### C. Inventory discrepancies

Differences that cannot yet be explained by confirmed fills or recorded transfers.

These are not interchangeable.

## Required repair

Implement an inventory discrepancy system.

Suggested fields:

```text
discrepancy_id
wallet_id
token_mint
expected_raw
observed_raw
difference_raw
detected_at
slot
evidence_source
resolution_status
resolution_reason
```

Suggested states:

```text
DETECTED
INVESTIGATING
EVIDENCE_FOUND
RESOLVED
NEEDS_ATTENTION
```

When a discrepancy occurs:

1. Record the discrepancy.
2. Preserve existing ledger quantities.
3. Pause conflicting trades on the affected inventory.
4. Inspect token accounts and available transaction history.
5. Attempt evidence-based reconciliation.
6. Reconcile only when sufficient evidence is obtained.
7. Alert operators when automatic resolution is not possible.

### Absolute prohibition

Do not automatically execute:

```text
wallet balance is lower
→ decrease oldest trade remaining_raw
→ mark position CLOSED
```

That is not valid evidence of a trading fill.

### Special handling

Investigate:

- Multiple token accounts
- Token transfers
- Token-2022 transfer fees
- Wrapped SOL
- Account closures
- Burn operations
- Wallet balance changes outside the bot
- RPC staleness
- Token-account ownership
- Concurrent pending transactions

Do not force unknown balance movements into BUY or SELL accounting.

# 7. P0 — WITHDRAWAL ENGINE V3

## Finding R9-004: Withdrawal callback remains non-atomic

R8 introduced withdrawal persistence but still uses a callback sequence resembling:

```text
Redis GET
   ↓
Execute transfer
   ↓
Redis DEL
```

Two concurrent callbacks may observe the same pending authorization.

## Required implementation

Build a durable withdrawal authorization and execution system.

### Withdrawal request lifecycle

```text
CREATED
   ↓
AUTHORIZED
   ↓
CLAIMED
   ↓
SIGNED
   ↓
SUBMITTED
   ↓
CONFIRMING
   ↓
TX_CONFIRMED
   ↓
RECONCILING
   ↓
RECONCILED
```

Exceptional states:

```text
FAILED
EXPIRED
UNKNOWN
NEEDS_ATTENTION
CANCELLED
```

Define permitted transitions explicitly.

### Mandatory safety properties

- A withdrawal request has a unique durable ID.
- The request belongs to exactly one authorized user.
- The intended wallet and destination are immutable after authorization.
- A request can be claimed only once.
- Concurrent callbacks cannot both authorize execution.
- Authorization is revalidated before signing.
- Destination restrictions and cooldowns are enforced.
- The signature is persisted before broadcast.
- Unknown broadcast outcomes remain tracked.
- The request is not considered completed before reconciliation.

### Database design

Use an atomic database claim.

Do not rely exclusively on Redis for withdrawal ownership.

Prevent conflicting pending or confirming withdrawals from consuming overlapping spendable balances.

Reserve a safe SOL amount for fees and rent where relevant.

### Atomic callback test

Execute 100 simultaneous callback requests against the same withdrawal authorization.

Expected:

- One request obtains execution ownership.
- No additional request can authorize a separate transfer.
- Database state remains valid.
- Replayed callbacks return a safe already-claimed response.

The test must prove ownership semantics, not merely count mocked function calls.

# 8. P0 — IMPLEMENT WITHDRAWAL RECONCILIATION WORKER

## Finding R9-005: `CONFIRMING` withdrawals can become permanently unresolved

R8 introduced durable withdrawal attempt records but the audit did not find a complete background reconciliation lifecycle for uncertain withdrawals.

## Required repair

Add withdrawal reconciliation to the existing recovery architecture.

The worker must process:

```text
SUBMITTED
CONFIRMING
TX_CONFIRMED
UNKNOWN
EXPIRED
RECONCILING
NEEDS_ATTENTION
```

Do not collapse all states into a generic timeout.

### Reconciliation procedure

1. Load unresolved withdrawal attempts.
2. Retrieve persisted transaction identity.
3. Query available on-chain evidence.
4. Evaluate confirmation status.
5. Validate transaction success or failure.
6. Verify relevant transfer effects.
7. Update the withdrawal ledger.
8. Finalize confirmed withdrawals.
9. Preserve uncertain withdrawals.
10. Escalate cases that cannot be resolved safely.

### Important Solana behavior

A transaction may have landed even if the client never received the RPC response.

An expired blockhash does not retroactively prove that a transaction failed.

A missing RPC result is not definitive evidence of non-execution.

If outcome is uncertain, preserve the reservation and prevent conflicting spending.

### Crash recovery requirements

Recovery must work when:

- The worker restarts.
- Redis restarts.
- PostgreSQL temporarily disconnects.
- RPC times out.
- The confirmation response is lost.
- The transaction lands before the client receives a signature response.
- The transaction was confirmed but the database update failed.

### Required tests

- Confirmed withdrawal, worker crashes.
- Submission timeout, transaction succeeds.
- Signature temporarily unavailable.
- Two workers reconcile the same withdrawal.
- Reconciliation runs twice.
- Withdrawal fails on-chain.
- Withdrawal expires with sufficient evidence.
- Outcome remains ambiguous.

No scenario may trigger an unintended replacement withdrawal.

A defect is considered `VERIFIED_FIXED` only when:

1. The original issue was confirmed or a valid failure reproduction was constructed.
2. The root cause was identified.
3. The code was repaired.
4. A regression test covers the defect.
5. The relevant test was actually executed.
6. The test passed.
7. Integration assumptions were verified where required.
8. No contradictory financial mutation path remains.

Use these issue statuses:

```text
VERIFIED_FIXED
IMPLEMENTED_NOT_VERIFIED
PARTIALLY_FIXED
UNRESOLVED
NOT_REPRODUCIBLE
BLOCKED_BY_ENVIRONMENT
```

Do not label a change `VERIFIED_FIXED` just because code was committed.
